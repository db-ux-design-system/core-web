## Conclusion

Three camps:

1. **Native `<dialog>`**: Porsche, Primer ViewComponents and KoliBri. Focus trap, top layer, `Esc` and `::backdrop` (by `closedby`) come from the browser. KoliBri is the clearest signal here: it actively deprecated its old `kol-modal` in favour of a native-`<dialog>` `kol-dialog`.
2. **`div role="dialog" aria-modal="true"` in a portal + hand-written focus trap**: everyone else (Atlassian, Bootstrap, Carbon, GitLab, MUI, MongoDB, Polaris, Mistica, Scale, SNCF). Many of these predate `<dialog>` being Baseline — but not all: SNCF's `wcs-modal` is actively developed, cites the APG dialog pattern in its own source, and still builds the `div` version by hand.
3. **Popover API**: SBB Lyne is the outlier: `popover="manual"` plus its own focus trap, `inert` and Escape handling — for both `sbb-dialog` and `sbb-overlay`, which share one base element.

Group 2 is legacy, not a recommendation — but the W3C does not say so for us. The [APG dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) still describes only the ARIA construction and ships a `div`-based reference example.

The argument for the native element comes from the [First Rule of ARIA Use](https://www.w3.org/TR/using-aria/#rule1) instead: prefer a native HTML element that already has the semantics and behaviour you need over re-purposing an element with an ARIA role. That matches our own approach to use native platforms functionality. On top of that, there is [no need to trap focus manually in a `<dialog>`](https://css-tricks.com/there-is-no-need-to-trap-focus-on-a-dialog-element/).

### What this means for us

We already ship a native-`<dialog>` implementation: `DBDrawer` uses `showModal()` / `show()`, `requestClose()`, `closedby`, `::backdrop`, invoker commands (`DBButton` with `command="show-modal" | "request-close"` + `commandfor`) and the `supportsClosedBy()` feature detection in `packages/components/src/utils/index.ts`. `DBDrawerHeader` already wires `aria-labelledby` onto the closest `<dialog>`.

So the honest first question is: **do we need a `DBDialog` at all, or is `DBDrawer` with an additional `direction`/`position` value enough?** A centred modal differs from a drawer only in placement and animation; the whole dialog lifecycle is identical, and none of the researched systems keep two separate JS implementations for it (Porsche shares one base across `modal`, `sheet`, `flyout` and `drilldown`). KoliBri does ship `kol-dialog` and `kol-drawer` as separate components, so that split is defensible; but note both wrap the same native element.

SBB Lyne makes the same call more explicitly: `sbb-dialog` (centred box) and `sbb-overlay` (page-covering) are two public components over a single shared base element that owns the whole open/close lifecycle. That is the shape to copy if we want a `DBDialog`: one base, thin components on top, rather than a second implementation.

If we do build a separate component, it should reuse the drawer's base rather than re-implement it (or else, the drawer might migrate to the DBDialog as it's inner element later on):

- native `<dialog>` + `showModal()`, no focus trap of our own
- `closedby="any"` for light dismiss, with the existing ponyfill for browsers in our [Browserslist](../../.browserslistrc) that lack it (`closedby` landed in Chrome 134, Firefox 141; Safari is the laggard)
- `aria-labelledby` from the heading, but we won't set `aria-describedby` to "connect" the body (only possible if we could ensure that the included contents would be very simple, which we can't); same mechanism as `DBDrawerHeader`
- slots for header / content / footer-actions, like Lyne, Carbon and Porsche

Findings / open questions:

- **`alertdialog`**: only Atlassian, MUI, MongoDB and Primer expose it. A native `<dialog>` needs an explicit `role="alertdialog"`. Do we need a `variant="alert"`, or is it enough to document the override?
- **Sizes**: most systems have a width scale (`small`/`medium`/`large`/`xlarge` or `maxWidth` + `fullScreen`); KoliBri instead takes a free-form `_width` capped at `100%`. We could reuse `DrawerContainerSizeList` instead of inventing a second scale.
- **Backdrop click**: Lyne makes it configurable (`backdrop-action="close|none"`), Carbon and MongoDB always close. `closedby="any" | "closerequest"` covers both natively; same as the drawer does today.
- **Non-modal**: Carbon documents modal _and_ non-modal dialogs. `dialog.show()` gives us that for free (the drawer already maps it to `backdrop="none"`).

### To align with concept, business engineering and design

Everything below is a decision the research surfaced but cannot answer on its own. Grouped by who has to answer it.

#### Concept

- **Do we need the component at all?** A centred dialog next to the existing `DBDrawer`, or is a placement variant of the drawer sufficient? Everything else depends on this answer.
- **Do we need a page-covering variant** (like SBB's `sbb-overlay`) in addition to a centred box, or does `DBDrawer` with `containerSize="full"` already cover that use case?
- **Dismiss rules**: may a dialog be closed by clicking the backdrop, or must the user pick an explicit action? Per use case or one system-wide default? (Lyne makes it configurable, Carbon and MongoDB always close, Shopify closes only via buttons.)
- **Opinionated confirm/alert flavour or free-form container?** Mistica ships only `alert`/`confirm`, MongoDB ships a dedicated `confirmation-modal`, everyone else takes arbitrary content. This decides whether we need `role="alertdialog"` support.
- **Nesting**: Shopify and KoliBri explicitly forbid stacked dialogs, the APG example demonstrates them. Do we forbid, discourage or support them?
- **Non-modal dialogs**: do we expose `show()` (page stays interactive) as a supported use case, or modal only?
- **Is a visible heading mandatory?** The APG requires an accessible name; KoliBri makes `_label` required. Do we enforce a heading, or allow a visually hidden label?
- **Is a visible close button mandatory?** The APG strongly recommends one; Scale and Washington Post make it optional. SNCF shows how that goes wrong: `showCloseButton="false"` also disables Escape, leaving no keyboard way out.
- **Content rules for destructive actions**: verb labels instead of "OK"/"Yes", consequences spelled out in the body, and which button gets initial focus (the APG suggests the least destructive one).
- **Do complex forms belong in a dialog** or on their own page? KoliBri advises against them, Shopify explicitly supports data entry.

#### Design

- **Size scale**: reuse `DrawerContainerSizeList` (`small`/`medium`/`large`/`full`), invent a dialog-specific scale (Shopify has five steps), or allow a free-form width (KoliBri)?
- **Narrow-viewport behaviour**: does the dialog go full-screen on small screens (Carbon, KoliBri, Primer's `position-narrow`), and at which breakpoint?
- **Backdrop**: which strengths do we offer and what is the default? The drawer already has `strong`/`weak`/`invisible`/`none` — SBB additionally distinguishes semi-transparent (keeps orientation) from fully covering.
- **Placement**: centred only (Shopify cannot be repositioned) or also top/bottom aligned (Primer's `align`)?
- **Motion**: enter/exit animation and the reduced-motion variant, including whether the existing drawer animation is reused.
- **Footer actions**: order of primary/secondary, wrapping vs. inline on narrow screens (GitLab exposes `keepActionsInline`), and whether a tertiary/cancel slot is needed.
- **Edge-to-edge content**: do we need a "no padding" escape hatch for images, tables or maps (Shopify's `padding="none"`)?
- **Visual base**: does the dialog reuse `DBCard` styling (KoliBri's `_variant="card"`) or bring its own container, corner radius and elevation?

#### Business engineering

- **Open/close contract**: declarative `open` prop, imperative `showModal()`/`close()`, or invoker commands (`command`/`commandfor`, which `DBButton` already supports)? Shopify went command-first. Which of these do we support and document?
- **Events**: which events do we emit and which are cancelable? Lyne and Shopify both offer before/after pairs; our drawer currently has `close` and `cancel`.
- **Return values**: do we expose a result on close (native `returnValue`, Lyne's `assignDialogResult`) so callers can distinguish confirm from cancel?
- **Forms**: is `<form method="dialog">` supported, and how do submit and validation interact with closing?
- **Framework parity**: identical behaviour across Angular, React, Vue and Web Components, plus SSR (no `HTMLDialogElement` on the server) and the `display:contents` host quirk we already work around in the drawer.
- **Stacking and top layer**: interaction with tooltip, popover and `DBCustomSelect` — we already carry a documented focus workaround for `<dialog>` and the top layer in `custom-select.lite.tsx`.
- **Ponyfill lifetime**: who owns removing the `closedby` fallback once it is evergreen for our [Browserslist](../../.browserslistrc) (there is already a `TODO` in `drawer.scss`)?
- **Migration**: is there an existing modal in consuming apps or an older DB UX version to migrate from, and does that need a migration guide plus a `major` changeset?
