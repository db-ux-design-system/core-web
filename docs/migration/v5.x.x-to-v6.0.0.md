# Migration (5.x.x) ➡ 6.0.0

## Dialog/drawer styles are no longer applied to the bare `dialog` element

The dialog/drawer base styles previously targeted the native `dialog` type
selector globally. They are now scoped to the component classes `.db-dialog` and
`.db-drawer` only.

**Why:** the global `dialog { … }` ruleset was emitted from
`styles/dialog-init.scss` as a side effect of importing that file for its
`$backdrop-color-*` SCSS variables. This leaked the ruleset into unrelated
component bundles (e.g. `loading-indicator`, `custom-select`) as dead CSS, and it
meant the design system styled **every** native `<dialog>` on a consumer's page,
not just DB components. The styles now live with the components that use them:
shared declarations in `styles/internal/_dialog-components.scss` (applied on
`.db-dialog` / `.db-drawer`) and drawer-only declarations in `drawer.scss`.

### What changed

<!-- markdownlint-disable MD060 -->

| Before                                               | After                                                     |
| ---------------------------------------------------- | --------------------------------------------------------- |
| `dialog { padding; margin; border; z-index; color }` | Applied on `.db-dialog` / `.db-drawer` only               |
| `dialog::backdrop` tint (strong/weak)                | Applied on `.db-dialog` / `.db-drawer` only               |
| `dialog[data-variant="inside"]::before` overlay      | Applied on `.db-drawer` only (drawer-only variant)        |
| `dialog[data-backdrop="invisible"]` rules            | Applied on `.db-drawer` only (drawer-only backdrop value) |

<!-- markdownlint-enable MD060 -->

The rendered output of `DBDialog` and `DBDrawer` themselves is unchanged. The
only functional difference is that a native `<dialog>` that is **not** a DB
component no longer receives these styles.

### How to migrate

If you relied on the design system styling native `<dialog>` elements that are
not `DBDialog` / `DBDrawer` (for example a plain `<dialog>` you render yourself),
scope the styling to those elements in your own stylesheet:

```css
dialog.my-dialog {
	padding: 0;
	margin: 0;
	border: 0;
	/* ...the resets you previously inherited... */
}
```

If you only use `DBDialog` and `DBDrawer`, no action is required.

## The `styles/dialog-init` Sass entry point was removed

`@db-ux/core-components/build/styles/dialog-init` is no longer published. It
previously existed only to emit the global `dialog { … }` ruleset (see above) and
to expose the `$backdrop-color-strong` / `$backdrop-color-weak` SCSS variables.

### How to migrate

- **If you imported it for its side effect** (the global `dialog` reset), remove
  the import. The reset is now applied by `DBDialog` / `DBDrawer` directly; a bare
  `<dialog>` of your own was never meant to be styled by it (see the section
  above for how to opt back in).
- **If you `@use`d / `@import`ed it for the `$backdrop-color-*` variables**, note
  that these moved to `styles/internal/_dialog-components.scss`:

    ```scss
    // Before
    @use "@db-ux/core-components/build/styles/dialog-init" as dialog;
    .my-overlay {
    	background-color: dialog.$backdrop-color-strong;
    }

    // After — the variables now live in an internal partial
    @use "@db-ux/core-components/build/styles/internal/dialog-components" as
    	dialog;
    .my-overlay {
    	background-color: dialog.$backdrop-color-strong;
    }
    ```

    `internal/*` is an implementation detail with no stability guarantee across
    minor/patch releases. If you depend on these backdrop colors long-term, prefer
    defining your own tokens rather than reaching into the internal partial.
