"@db-ux/core-eslint-plugin": minor

feat: add `dialog-header-required` rule to the recommended config

- New `dialog-header-required` rule: reports a `DBDialog` usage whose `header` slot does not contain a `DBDialogHeader` (React, Angular, Vue).
- `sub-component-required-parent` now covers `DBDialogHeader` and `DBDialogFooter`, `close-button-text-required` now covers `DBDialogHeader`.
- `sub-component-required-parent` no longer reports React sub-components whose placement cannot be verified statically (e.g. extracted into a variable `const header = <DBDialogHeader />` and passed via `header={header}`), matching how `dialog-header-required` treats dynamic slot values.
- `dialog-header-required` no longer accepts `slot="header"` in Angular templates: Angular projects the named region via `<ng-content select="[header]">`, so only the `header` attribute enters the slot. This aligns the rule with `sub-component-required-parent`.
- `text-or-children-required` now covers `DBDialogHeader` and `DBDrawerHeader`, so a header without `text` or children is reported (it would otherwise leave the dialog without an accessible name via `aria-labelledby`).
    - An empty or whitespace-only `text` value (e.g. `text=""`, including its Angular/Vue equivalents) counts as missing content, not as a valid title.
    - A React expression child that renders nothing (e.g. `{null}`, `{false}`, `{undefined}`, `{''}` or an empty template literal) likewise counts as missing content, while a dynamic expression such as `{title}` is left as unresolvable content.
    - A React spread (`<DBDialogHeader {...headerProps} />`) or Vue object `v-bind` may supply `text`, so a header with no explicit `text` or children but such a spread is treated as unresolved rather than reported (a later explicit `text` still wins and is validated) - matching how `close-button-text-required` handles spreads.
    - An Angular heading nested in a structural directive (`*ngIf`) or built-in control flow (`@if`, `@for`, `@switch`) is recognized: the parser wraps it in a Template/block node, so the rule recurses through those wrappers instead of reporting the valid conditional heading as missing.
- `dialog-header-required` no longer reports a `DBDialog` that receives a JSX spread (e.g. `<DBDialog {...dialogProps}>`), because the spread may supply the `header` prop and its contents cannot be verified statically.
- `close-button-text-required` now reports a statically empty or null close-button label passed as an expression (e.g. `closeButtonText={''}`, `closeButtonText={\`\`}`,`closeButtonText={null}` or a whitespace-only literal in React, and the equivalent empty/null Angular/Vue bindings). These previously slipped through as unresolvable dynamic content even though the icon-only close button and its tooltip render without an accessible label.
- `close-button-text-required` no longer reports a React header whose `closeButtonText` may come from a JSX spread, matching how the header-required rules treat spreads. It compares the last explicit-attribute and spread positions, so only the one that determines the final React prop is validated: a spread after the last `closeButtonText` leaves it unresolved (e.g. `<DBDialogHeader {...headerProps} />` or `<DBDialogHeader closeButtonText="" {...headerProps} />`), while a later explicit `closeButtonText` wins and is validated (including an explicit empty value).
- `close-button-text-required` extends that spread handling to a Vue object `v-bind` (e.g. `<DBDialogHeader v-bind="headerProps" />`): the argumentless bind may supply `closeButtonText`, so the header is treated as unresolved. Vue later-wins is respected too - an object `v-bind` after the last explicit `close-button-text` leaves it unresolved, while a later explicit value wins and is validated (an explicit empty value is reported).
- `close-button-text-required` now registers the Vue parser's fallback `Element$1` node type as a visitor root, so a component exposed as that node (e.g. `DBDialogHeader`) still runs the close-button label check instead of letting an empty `closeButtonText` bypass this recommended accessibility rule (matching the header-required rules, `text-or-children-required` and `sub-component-required-parent`).
- `dialog-header-required` and `drawer-header-required` now recurse through Angular structural-directive wrappers, so a conditional projected header (e.g. `<db-dialog-header *ngIf="show" header>`) is recognized. The Angular parser wraps such an element in a `Template` node, which the projection search previously skipped, wrongly reporting the valid header as missing.
- `dialog-header-required` and `drawer-header-required` now include the Vue parser's fallback `Element$1` node type in the named-slot template and descendant checks, so a valid `#header` slot exposed through that fallback node is no longer reported as missing.
- The shared Angular visitor factory now registers both `Element` and `Element$1` selectors, so every Angular rule built on it (e.g. `dialog-header-required`, `drawer-header-required`, `sub-component-required-parent`) still runs when the parser exposes a component as the fallback `Element$1` node - previously such a component was silently skipped.
- `sub-component-required-parent` now walks the Vue parser's fallback `Element$1` node type in the parent chain, so a correctly placed `DBDialogHeader`/`DBDialogFooter` whose slot template or `DBDialog` ancestor is exposed through that fallback node is no longer reported as orphaned (the Angular path already handled `Element$1`).
- `dialog-header-required` and `drawer-header-required` now validate an explicit `header` prop that follows a JSX spread. Because React applies the later value, `<DBDialog {...props} header={null}>` renders no header and is reported; a spread only suppresses the check when it (not a later explicit `header`) determines the final value.
- `dialog-header-required` and `drawer-header-required` now recurse into JSX expression containers nested inside a `header` prop wrapper, so a conditional header wrapped in a fragment or element (e.g. `header={<>{show && <DBDialogHeader>Title</DBDialogHeader>}</>}`) is treated exactly like the same expression used directly instead of being reported as missing.
- `drawer-header-required` now shares the same `createHeaderRequiredRule` factory as `dialog-header-required` instead of a duplicated implementation, so the two rules cannot drift and every parser, control-flow and spread fix reaches both. Behavior is unchanged.
- `dialog-header-required` and `drawer-header-required` now recurse through a React node array passed as the `header` prop (e.g. `header={[<DBDialogHeader key="h">Title</DBDialogHeader>]}`), which React renders normally. The array previously fell through to the dynamic-type check and was reported as missing; a statically inspectable array without the header component (e.g. `header={[<div />]}`) is still reported.
- `dialog-header-required`, `drawer-header-required` and `sub-component-required-parent` now treat only the _destination_ of a dynamic Vue slot argument (`<template #[slotName]>`) as statically unresolved: the slot name is a `VExpressionContainer` that cannot be resolved at lint time, but the slot's content is statically visible, so the rule still requires the header component to appear inside it. A dynamic slot holding a real `DBDialogHeader` is accepted (only where it lands is unknown); a dynamic slot holding plain markup with no header anywhere is reported. This also fixes a latent crash on any non-string slot argument.
- `text-or-children-required` now inspects statically empty Vue interpolation children: `<DBDialogHeader>{{ null }}</DBDialogHeader>` and `{{ '' }}` (and a whitespace-only template literal) count as missing content, while `{{ title }}` stays unresolvable and `{{ false }}`/`{{ true }}` remain content because Vue renders those as text (unlike React).
- `text-or-children-required` now registers the Vue parser's fallback `Element$1` node type as a visitor root, so an empty `DBDialogHeader`/`DBDrawerHeader` exposed through that fallback node still runs through this recommended accessibility check instead of being silently skipped (matching the header-required rules). Its child-content check now counts both the `Element` and `Element$1` element fallbacks (alongside `VElement`), so a header whose child element is exposed as either fallback (e.g. `<DBDialogHeader><span>Title</span></DBDialogHeader>`) is recognized as content instead of being reported as empty.
- `text-or-children-required` now recurses into a React fragment child, so `<DBDialogHeader><>Title</></DBDialogHeader>` (which React renders as a nonempty accessible name) is recognized as content instead of being reported. An empty fragment, or one whose children all render nothing (e.g. `<>{null}</>`), still counts as missing content.
- `sub-component-required-parent` now accepts a slot-less sub-component rendered through a transparent inline array, e.g. `<DBAccordion>{[<DBAccordionItem />]}</DBAccordion>`. The direct-child check previously compared the original array node against the parent and wrongly reported the item as orphaned; it now carries the unwrapped relationship into that check, so the same array inside a non-parent element (e.g. `<div>{[<DBAccordionItem />]}</div>`) is still reported.
- `sub-component-required-parent` now registers the Vue parser's fallback `Element$1` node type as a visitor root, so a sub-component (e.g. `DBDialogHeader`/`DBDialogFooter`) exposed as that node still runs through the placement check instead of being silently skipped. Walking `Element$1` ancestors did not help when the root sub-component itself was never visited (matches the header-required rules and `text-or-children-required`).
