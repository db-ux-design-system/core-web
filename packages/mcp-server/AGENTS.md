# MCP Server Development Rules

When working on the `@db-ux/mcp-server` package, these rules are **mandatory**:

- **ESM only**: The package is `"type": "module"`. **NEVER use `require()`** — use `import` (top-level or dynamic `await import()`). Using `require()` will crash at runtime.
- **MCP SDK v2 package split**: The single `@modelcontextprotocol/sdk` package is gone. Import `McpServer` from `@modelcontextprotocol/server`, the stdio serving entry from `@modelcontextprotocol/server/stdio` (the root barrel deliberately does not export it), and the test client from `@modelcontextprotocol/client` / `@modelcontextprotocol/client/stdio`. Never re-add `@modelcontextprotocol/sdk` — it is frozen on the 2025-era protocol.
- **Zod 4 only, always wrapped**: SDK v2 dropped zod 3 support. **Never import from `zod/v3`** and never pass a raw `{ field: z.string() }` shape as `inputSchema` / `argsSchema` — wrap it in `z.object({ ... })`. A raw shape built with a foreign zod fails at registration or silently breaks the first `tools/list`; a zod-3 schema typechecks fine and only fails at runtime.
- **Keep `zod` in lockstep with the SDK**: the SDK declares `"zod": "^4.2.0"`, this package pins it exactly, and both are bundled. Bump them together (they share the `modelcontextprotocol` Dependabot group) so the resolver keeps one copy. Schema conversion runs through zod's `~standard.jsonSchema`, so a second copy at >= 4.2 still interoperates, but below that the SDK falls back to its own lossy converter and warns.
- **Factory, never a module-level singleton**: `serveStdio` decides the connection's protocol era and pins the instance it serves for that connection's lifetime. Register every tool and prompt inside `buildServer()` in `src/server.ts`. **Never register as a module side effect** and never export a shared `McpServer` instance — registrations outside the factory are invisible to the served instance. The factory can run more than once per connection (a `server/discover` probe gets its own instance, discarded on fallback to `initialize`), so it must stay side-effect free and must not hand out shared mutable state.
- **Always pass `onerror` to `serveStdio`**: it is the only channel for out-of-band failures. A rejected `transport.start()` is reported through the callback and then swallowed, so without it a server that never came up looks exactly like a healthy one.
- **Set `cacheHints` for the list results**: tool and prompt lists are static per package version. Without hints the SDK emits `ttlMs: 0` / `cacheScope: 'private'` and 2026-07-28 hosts cache nothing.
- **Both protocol eras are served**: `serveStdio` keeps the `legacy` option at its default (`'serve'`), so hosts on the 2025 era (`initialize` handshake) and on 2026-07-28 (`server/discover` probe) both work. Do not set `legacy: 'reject'` — it would break every host that has not adopted 2026-07-28. Cover both eras when changing the serving path; `e2e.test.ts` pins `2026-07-28` for the modern suite, and a pin never falls back, so it fails loudly on regressions.
- **A claim-less request is a 2025-era opening**: a raw `server/discover` without the `io.modelcontextprotocol/protocolVersion` `_meta` envelope key is correctly answered with `-32601`. When smoke-testing the modern era by hand, send the envelope — or just use the SDK client with a pin.
- **No NPM lifecycle hooks**: `prebuild`/`preinstall` hooks are disabled in this monorepo. Chain build steps with `&&` in the `"build"` script (e.g. `"build": "node scripts/prebuild.ts && node esbuild.js"`).
- **Build scripts**: Build scripts currently run TypeScript helpers via `tsx` (e.g. `scripts/prebuild.ts`). Keep this `AGENTS.md` and `package.json` aligned if the build tooling changes.
- **Never commit build artifacts**: Files in `assets/migration/` and `assets/tokens/` are generated by the prebuild script. They are git-ignored and must never be committed.
- **Hard CI failures**: Build scripts must `throw new Error()` when required source files are missing. Never `console.warn()` and continue — this causes incomplete packages to be published. Exception: the density CSS file is a build artifact that may legitimately not exist before foundations is built.
- **Strict assets-only reading**: The server must never fall back to monorepo source paths (`packages/foundations/...`) at runtime. Read strictly from `assets/` to avoid masking build failures.
- **Never hardcode a relative path to `assets/`**: use the `ASSETS_DIR` constant from `src/utils/path.ts`. The depth differs between the sources (`src/tools/`) and the bundle (esbuild flattens everything into `dist/index.js`), so `../../assets` is right in one layout and points outside the package in the other. The failure is silent — `list_visuals` reports an empty directory and `get_design_tokens` falls back to raw SCSS, both without an error.
- **Source-only tests cannot catch bundle bugs**: every suite except `bundle.test.ts` spawns `src/index.ts` through tsx. Anything that depends on the on-disk layout must be covered by `bundle.test.ts`, which runs the built `dist/index.js` — that is the artifact consumers get from `npx`.
- **File system safety**: After `stat()`, always check `stats.isFile()` before calling `readFile()`. Passing a directory path to `readFile()` causes an unhandled `EISDIR` error that crashes the server.
- **Cross-platform paths**: Always normalize backslashes to forward slashes before path comparisons. Windows manifest keys contain `\` which breaks `.includes('/')` checks.
- **DB UX v2 terminology**: In v2, `cmp-*`, `elm-*`, `rea-*` were **CSS classes**, not HTML tags. The actual custom elements were `<db-*>`. Do not confuse these in migration docs or scanner descriptions.
- **DB UX v3 HTML markup**: Use CSS classes (`class="db-card"`, `class="db-button"`) with `data-variant` for variants and `type="button"` on buttons. Do not invent attributes like `data-variant="card"` on divs.
